# Telegram global search — design & plan

This is the implementation plan. The feasibility findings live in
[research/telegram-global-search.md](research/telegram-global-search.md).

## Authentication options
| Option | Global public search? | Verdict |
|---|---|---|
| Bot API (bot token) | **No** | unusable for global search |
| MTProto user account (Telethon) | **Yes** (`channels.searchPosts`) | **required** |

→ We must authenticate Telethon with a **user account** session string.

## Telethon plan
- `search_global_telegram_posts` (sharedPool) builds a Telethon client from
  `context["secrets"]` (`TELEGRAM_API_ID`, `TELEGRAM_API_HASH`,
  `TELEGRAM_SESSION_STRING`) and calls
  `functions.channels.SearchPostsRequest(hashtag=... | query=..., ...)`.
- Implemented in `src/clip2trace/telegram_live.py` (`TelethonSearchClient` +
  `build_client_from_secrets`): pure query-routing / normalisation / pagination
  logic (unit-tested without Telethon) plus a thin, lazily-imported Telethon
  glue. `build_client_from_secrets` returns `None` when Telethon or any secret is
  missing, so the function reports `live_unavailable` instead of faking a search.
  The deployable `sinas-package.yaml` inline `code:` block carries a
  self-contained mirror of this logic (the sandbox can't import clip2trace), kept
  runnable in demo mode and guarded by `tests/test_package_inline_sync.py`.
- Exactly one of `hashtag` / `query` per call. Prefer **handle/hashtag** queries
  (unmetered) over free-text (metered → Stars).
- Paginate with `offset_rate`/`offset_peer`/`offset_id`; read `next_rate`.

## Session storage plan
1. Run `scripts/bootstrap_telegram_session.py` locally (interactive) → prints a
   `StringSession`.
2. Store it as the Sinas secret `TELEGRAM_SESSION_STRING` (+ `TELEGRAM_API_ID`,
   `TELEGRAM_API_HASH`). Never commit. Rotate if leaked (it = full account access).
3. Enable `ENABLE_TELEGRAM_LIVE_SEARCH=true` on the package.

## Query strategy
Generated by `generate_telegram_queries` / the telegram-query-planner agent:
1. `handle` (exact @handle / watermark) — strongest, unmetered.
2. `ocr_exact` (verbatim on-screen text).
3. `context` (caption / topic terms).
4. `hashtag` — unmetered global path.
Emit a *small* ranked set; do not spam.

## Rate-limit / flood-wait handling
- Catch `FloodWaitError`; respect `.seconds`; exponential backoff above a
  threshold; cap total attempts per job.
- Cache `query → results` in the `clip2trace/query-cache` store to avoid
  repeat live calls.
- Call `channels.checkSearchPostsFlood` before free-text searches; skip/queue if
  no free slots and Stars-spend is not authorised.

## Paid / full-text caveats
Free-text global search consumes free daily slots, then costs Telegram Stars.
We default to **not** spending Stars; free-text falls back to hashtag/handle
queries unless an operator explicitly authorises paid search.

## Fallback / demo mode
`search_global_telegram_posts` resolves in this order: `manual_urls` →
`cached_results` → live (if enabled + secrets present) → explicit
`live_unavailable` / `demo_no_data` status with diagnostics. The demo uses
`cached_results` so it never depends on a live account.

### Third-party managed-search fallback (#28)
`search_posts(..., fallback_provider=...)` accepts an optional provider that runs
**after** the direct Telethon path fails/is unavailable and **before** cached.
`src/clip2trace/telegram_search_providers.py` ships `HttpSearchAdapter` — a
generic adapter that duck-types `search(queries)` (same contract as the live
client) and POSTs to a managed Telegram-search service; the concrete wire format
is pluggable via `build_request` / `parse_results`, so a specific provider is
optional. Configure via Sinas variables `TELEGRAM_SEARCH_API_URL` (text) +
`TELEGRAM_SEARCH_API_KEY` (secret); `build_search_fallback_from_secrets` returns
`None` when unset (fallback simply skipped). Results are tagged
`source: "third_party"` and are still **retrieval, not proof** — visual
verification decides.

## Compliance
Provenance/source-tracing use only. Respect Telegram ToS; use a dedicated
account; store only what the feature needs; no scraping of private/restricted
content. See [risks.md](risks.md).
